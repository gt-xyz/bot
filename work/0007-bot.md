---
title: The tool is bot; a project is a repository; a session is a running agent
---

`bee` was a metaphor, and a metaphor is a word every newcomer has to
translate. The tool is `bot`, which is what the agent account on the forge is
already called. Three nouns and nothing else:

- A **project** is a repository with a few lines of configuration: profile,
  egress policy, status, remote. Its durable home is the remote. Nothing on
  the host is canonical.
- A **session** is one agent running in one container on one project. It has
  a start, a transcript, a branch, and an end. It takes messages and emits
  events, so you can talk to any running session from the web face or a
  terminal. `bot up` starts one waiting for your first message; `bot run`
  starts one with the next piece of work as its first message. Same thing.
- An **agent** is the program inside a session: a hosted model's CLI, an open
  harness on a key-based provider, or one on a model served on the fleet. Any
  of them, chosen when the session starts, wrapped to one contract (0013).

**Projects and sessions are separate things.** A project has had zero or many
sessions; a project can have several running at once. Each session gets its
own fresh clone of the remote on its own branch, so two sessions never share a
tree and removing a finished session is deleting a directory. This replaces
the one working copy per project that `bee` kept on the host, and it is what
makes concurrency free and containment simple: a session's container mounts
its own clone and nothing else.

Derived, never stored, as the project doc says: a project's state comes from
its remote, a session's state comes from the container runtime and its log.

| command                       | does                                                   |
|-------------------------------|--------------------------------------------------------|
| `bot init <project>`          | scaffold, commit, push (was `bee new`)                 |
| `bot up <project>`            | start an attended session and attach                   |
| `bot run <project>`           | start an unattended session on the next piece of work  |
| `bot attach <session>`        | attach to any running session, attended or not         |
| `bot stop <session>`          | stop a session, keep its log                           |
| `bot ls`                      | the board: projects, their sessions, their pull requests|
| `bot log <session>`           | the session's log so far                               |
| `bot check`                   | prove the guarantees in 0008 hold on this host         |
| `bot serve`                   | the web face, the primary face (0011)                  |

`init` rather than `new`, because `bot new life` reads as a new bot, and
`init` already means "make this a project". `check` rather than `doctor`,
because it is the word the test script uses.

Rejected names for the tool: `hive`, the metaphor again with the tool as the
building; `jobs`, a shell builtin; `dev`, the folder the projects live in and
too common to search for; `agent`, which collides with every other agent on a
machine. `bot` is generic too, and for a single-user tool that costs nothing.

The rename touches the binary, the config directory (`~/.config/bot`), the
image names (`bot-base`, `bot-cpp`, `bot-scratch`) and the project doc. The
scaffold names no vendor and no tool: `AGENTS.md` and `docs/` do not mention
bot, so a project survives the tool being renamed again.
